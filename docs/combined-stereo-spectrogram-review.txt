Combined stereo spectrogram: feature and contributor review guide
Review checkpoint: 2026-10-24

Purpose
Display the left and right spectral levels together in one spectrogram pane.
Each channel contributes independently, so a quieter channel does not disappear
merely because the other channel exceeds a fixed balance threshold.
The feature reuses Audacity's existing FFT spectra and display gain/range settings.
Changing a palette does not modify source audio or introduce another FFT analysis.

What the colors mean
Red / blue: left is red, right is blue, equal displayed levels blend to purple.
Magenta / green: left is magenta, right is green, equal levels blend to gray/white.
Orange / blue: left is orange, right is blue, equal levels blend to gray/white.
Both channels at the display floor are black; equal levels brighten together.
A dark pixel can mean below the chosen display floor, rather than literal silence.
The mode is restricted to the Frequencies algorithm; mono uses ordinary rendering.
The controls provide a palette choice and a fixed mapping, without a balance-contrast knob.

Signal interpretation and information loss
These are paired spectral levels, not phase, polarity, correlation, or stereo width.
Equal powers can occur with signals having different or opposite phases.
Equal overall channel loudness does not imply equal levels at every frequency.
Each displayed frequency row may span several FFT bins. The representative bin is
chosen by the largest single-channel level: max(leftDb, rightDb), first bin on ties.
Both channel values are then read at that SAME bin to avoid pairing unrelated peaks.
For example, left-only and right-only peaks in different bins can fall in one row.
The stronger peak wins; the other peak can be discarded at that display resolution.
This is peak-feature rendering, not a sum of all the power within the frequency row.
Display clipping, row pooling, RGB8 quantization, and lookup interpolation lose data.
The continuous design should not be described as lossless displayed pixels.

Mapping to display color
1. Normalize each cached dB value using the same gain and range:
   u = clamp((db + range + gain) / range, 0, 1).
2. Apply the same fixed curve f(u) = u / (3 - 2u) to each channel.
   It maps 0 to 0, 0.5 to 0.25, and 1 to 1; it reserves bright mixtures for strong pairs.
   This is a chosen display curve, not a physical amplitude decoder or unique best scale.
3. Form base encoded RGB: (L,0,R), (L,R,L), or (L,0.4L+0.6R,R), respectively.
4. Decode sRGB, then expand color differences about a same-luminance neutral.
   Gray is the neutral for magenta/green and orange/blue; red/blue uses purple in G=0.
   Expansion uses 5/(1+4r), with r the fraction of available gamut radius.
5. Encode sRGB and dim selected colors by 0.72 without reversing channel identities.
6. Use a precomputed 256-by-256 table for each palette and selection state.
   Bilinear interpolation avoids snapping channel levels to the nearest table cell.
The floating-point gamut expansion preserves luminance relative to the POST-CURVE
base color. The curve changes brightness; selection, quantization, and interpolation
mean final RGB8 pixels do not have exactly preserved luminance.
The table is heap-backed and initialized once; cold initialization is separate from warm painting.

Color vision and displays
No palette here is certified safe for every color-vision deficiency or display.
Alternative palettes help users choose, but do not replace labels and ordinary views.
Monitor primaries have spectral distributions; RGB values are not isolated cone channels.
Purple is a mixture, not a single wavelength. Display color does not encode an optical
frequency corresponding to the audio frequency on the spectrogram's vertical axis.
Color-vision simulations are screening tools, not proof of an individual's perception.
Review the final transform with affected users, including small/dim features and selection.

Reproducing native tests
Follow BUILDING.md for the normal toolchain, Qt, dependency, and build configuration.
Enable MUSE_ENABLE_UNIT_TESTS=ON and AU_BUILD_SPECTROGRAM_TESTS=ON in that configuration.
cmake --build <build-dir> --target spectrogram_tests
ctest --test-dir <build-dir> -R "^spectrogram_tests$" --output-on-failure
Use an appropriate Qt runtime/plugin search path. A headless test environment may use
QT_QPA_PLATFORM=offscreen; this does not substitute for GUI interaction tests.

Contribution process and accountability
Read AI_POLICY.md and CONTRIBUTING.md at the repository root before requesting review.
AI_POLICY.md requires contributors personally to read, review, and understand generated
code and text, including comments, and remain able to answer questions about the work.
An automated review does not meet that personal responsibility for the contributor.
Write the PR description yourself; the policy strongly recommends this approach.
Substantial AI assistance requires the PR template's AI field, tool name, and relevant
commit trailers: Assisted-by: <tool name> <version, if known>.
Use Assisted-by:, not AI Co-authored-by:. Sign the Audacity CLA as required by CONTRIBUTING.md.
Review the current .github/pull_request_template.md for its remaining requirements.
Discuss this feature before upstream submission; the template offers an issue-link field,
but that alone is not a blanket requirement to create an issue for every contribution.
The contributor remains responsible for licensing, correctness, validation, and public text.
